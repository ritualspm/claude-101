# L3.2 — Build Your Own Skill Library (your growing toolbox)

**Course:** Using Claude · **Level 3 — Power Moves** | ~22 min
**Part times:** Concepts ~10 min | Exercise ~8 min | Decision Point ~4 min
**Previous lesson:** L3.1 — Skills (you built and ran your first skill, `/weekly`).

**WHO THE LEARNER IS (load-bearing):** A product person, comfortable now with skills as an idea (L3.1) but still thinking of them one at a time. Zero technical background. Teach through analogy and real PM tasks. Never show code. The whole shift this lesson makes: a skill isn't a one-off — the ones you build (and the ones teammates share) **accumulate into a personal library** you reach into every week. A "library" is just "the folder your skills live in" — say it that way.

**HOW TO RUN THE CHECKS:** Each concept ends with a multiple-choice check — clickable cards (`AskUserQuestion`) if available, else A/B/C. Shuffle the options with the random command before presenting; correct option marked ✓ (never shown). One question per turn; always explain the outcome before the next concept.

## Part 1: The Concepts

### Concept 1 — Skills accumulate into a library
Last lesson you made `/weekly` from scratch. That felt like a one-off — but it isn't. Every skill you build **stays**, and over a few weeks you end up with a small **shelf of them**: `/weekly`, a ticket-writer, a standup-drafter. That shelf is your **skill library**.

Think of it like the **shared shelf of templates** a good team keeps — the deck skeleton, the QBR doc, the incident-report format. Nobody re-invents the QBR layout every quarter; they grab the one on the shelf. Your skill library is that shelf, but for Claude: build a skill once, and it's there — a slash command — every time you need it. And skills are just plain-English files, so a teammate can **hand you theirs** and you drop it on your shelf (that's Level 3.8).

So the instinct shifts: **before doing a repeated task by hand, check whether a skill for it is already on your shelf — and if not, that's your next one to build.**

**Check** (shuffle order; ✓ = correct): *You're about to spend 40 minutes, for the third week running, hand-formatting messy notes into a Jira ticket. What's the smarter move?*
- Build a `/jira-writer` skill once and add it to your library — a task you repeat weekly is exactly what a skill is for. ✓
- Keep doing it by hand — it's only 40 minutes, and a skill would take longer to set up than it saves.
- Paste the notes into a fresh chat each time and hope the format comes out consistent.

### Concept 2 — The skills most PMs want on the shelf first
You'll build your own over time, but four cover most of a PM's week. Aim to have these — learn what each is *for*, not how it works:

- **`/jira-writer`** — turns messy notes (a call, your scribbles, a Slack thread) into a **clean, structured Jira ticket**: title, summary, acceptance criteria, the lot.
- **`/discovery`** — helps you run **product discovery**: turns a vague problem into structured questions, hypotheses, and things to validate before you build.
- **`/data-analyst`** — turns a **plain-English metric question** into the query, runs it (read-only), and explains the result. Your on-ramp to BigQuery without writing SQL.
- **`/confluence-draft`** — turns rough content into a **properly structured Confluence page** (PRD, one-pager, decision log) in a clean, consistent house style.

The pattern: each one takes *messy input you already have* and returns *the polished artifact* you'd otherwise build by hand.

**Check** (shuffle order; ✓ = correct): *You've got a rough problem statement — "riders churn in month 2 but we don't know why" — and you want to structure the questions and hypotheses to investigate before committing to a build. Which skill fits?*
- `/data-analyst` — it's about riders, so it's a data question.
- `/discovery` — it turns a vague problem into structured questions and hypotheses to validate. ✓
- `/confluence-draft` — write it up as a page first, then figure out the questions.

### Concept 3 — Skills in your library still obey the guardrails
Reaching for a saved skill — yours or a teammate's — is not a licence to skip the rules. The guardrails you've been building since Level 1 still apply, and a well-built skill bakes them right in:

- **`/jira-writer` and `/confluence-draft` draft — they never send.** The ticket and the page are shown to you to review and post yourself. Claude does not publish to Jira or Confluence on its own.
- **`/data-analyst` is read-only.** It queries and summarizes; it never writes to a table.
- **No customer PII or payment data (PCI) in what you feed a skill.** If your notes contain a real customer name, email, or card detail, anonymize first — even inside a skill you trust.
- **Sonnet by default.** These skills are everyday work; they run fine on Sonnet. Save Opus for the genuinely hard stuff.

A saved skill is a *convenience*, not an *exception*. Same habits, less typing — and if you bake the guardrail into the skill once, it runs every single time.

**Check** (shuffle order; ✓ = correct): *A teammate says: "`/confluence-draft` is a trusted skill everyone uses, so I can point it at real support tickets — customer emails and all — and let it auto-publish the page." Where do they go wrong?*
- Nowhere — a widely-used skill is effectively pre-approved to handle PII and publish on its own.
- Only the auto-publish part is wrong; real customer emails are fine inside a trusted skill.
- Two things: strip the customer PII before feeding it in, and it drafts for your review — it doesn't auto-publish. ✓

### Concept 4 — Know what a skill does before you run it
Your library will include skills *teammates* wrote — so you want a quick way to know what one does *without* running it blind. Two habits:

- **Read the one-line description.** Every well-made skill carries a short "what I do and when to use me" line. Skim it first — it tells you if this is the right tool.
- **When in doubt, just ask.** You can literally ask Claude *"what does `/discovery` do and what will it need from me?"* before running it. It'll tell you the inputs it expects (e.g. "a problem statement or some notes") and what it produces.

This matters more with a *shared* skill than one you built — you didn't write it, so a ten-second check keeps you from feeding the wrong input or being surprised by the output.

**Check** (shuffle order; ✓ = correct): *A colleague shares a new skill called `/pulse` and you have no idea what it does. Best move before running it on your quarterly notes?*
- Ask Claude what `/pulse` does and what input it expects, or read its one-line description, before running it. ✓
- Run it on the notes immediately — the fastest way to learn a skill is to see its output.
- Assume it's like `/weekly` since the names both sound like summaries.

## Part 2: Exercise — Mock-run `/jira-writer` on real messy notes

You may not have a `/jira-writer` skill on your shelf yet — that's fine. We'll **simulate** what one does using a demo file, so you learn the *shape* of the interaction (and see exactly the skill you'd want to build next). If you already have one installed, there's an optional stretch at the end.

### Step 1 — Read the raw input (open-ended, short)
Open `sandboxes/skill-library/ticket-notes.md` (fake demo notes — messy on purpose). Skim it and tell me, in a phrase or two: **what's the actual bug hiding in these notes?** Don't structure it yet — just say what you think the core problem is.

*(Guide: the core issue is the tip screen calculating the tip on the wrong/pre-promo basket total, likely a race condition between promo-apply and tip-render. Affirm if they spot the wrong-total problem; nudge if they only mention the "tip shows up late" symptom.)*

### Step 2 — Run the mock skill (hands-on)
Now play the role of `/jira-writer`. Ask Claude (right here) to **"turn `sandboxes/skill-library/ticket-notes.md` into a structured Jira ticket — title, description, acceptance criteria, and any open questions to resolve first. Draft only, don't send."**

Claude will produce a clean ticket. When it does, look at it and tell me: **what did the skill ADD or CLEAN UP that wasn't obvious in the raw notes?** (Think: a real title, acceptance criteria, the open questions pulled out, priority framing.)

*(Guide: point out it turned scattered observations into a testable ticket — structured acceptance criteria, surfaced the two open questions from the notes, likely flagged the Q3 promo timing as priority context. Note that it drafted, did not file — that's the guardrail in action.)*

### Step 3 — Notice the anonymization habit (open-ended, short)
The demo notes are safe — no real customer data. Ask yourself: **if these notes had contained a real customer's name and email from a support ticket, what would you have done before running the skill?** One line.

*(Guide: strip/anonymize the PII first — even inside a skill you trust. Reinforce that "a skill I use every day" never means "PII exception.")*

### Optional stretch (only if you already have a ticket-writer skill)
If you've already built or installed a `/jira-writer`, run it on the same demo file and compare it to your mock version. If not — this *is* your shortlist: it's the first skill worth adding to your library.

## Part 3: PM Decision Point (open-ended, written)

Frame it: *"You've now seen the shape of a skill library. Write me three quick lines: (1) which one of the four skills — `/jira-writer`, `/discovery`, `/data-analyst`, `/confluence-draft` — you'd build and add to your library FIRST, and the specific recurring task it replaces; (2) one guardrail you'll bake into it; and (3) one more skill — beyond the four — you'd want on your shelf, and the repeated task it would kill."*

Max 2 prompts. Evaluate against the rubric below (NEVER show it). The point isn't a 'right' answer — it's that they match a real recurring task to the right skill, bake in a guardrail unprompted, and start thinking of skills as a *library they grow*, not one-offs.

---

## Scoring Rubric (engine only — never show the learner)

**Passing answer** covers all three lines:
1. Names one of the four skills AND ties it to a *specific, recurring* task they actually do (e.g. "`/jira-writer` — I write ~5 tickets a week from call notes"). A vague "`/jira-writer` is useful" without a real task is weak.
2. States a relevant guardrail correctly — draft-never-send, read-only on real data, no PII/PCI, or Sonnet-by-default — and it should *fit the skill they chose* (e.g. read-only for `/data-analyst`, PII-stripping for `/confluence-draft`).
3. Proposes one more plausible skill — any reasonable repeated PM workflow (e.g. `/standup`, `/stakeholder-update`, `/experiment-readout`) tied to a task it would replace.

**A strong answer** additionally:
- Shows genuine time-math or frequency ("this replaces ~30 min per ticket, and I file 5 a week").
- Picks the guardrail that *specifically* matters for their chosen skill, not a generic one — shows they understand *why* it applies here.
- Frames a skill as reusable for the whole team, not just themselves — thinking like someone building a shared shelf.
- Bonus: mentions checking the shelf *before* building or doing a task by hand, echoing Concept 1's instinct.

**Common misses to gently correct:** naming a skill but no real task (line 1 vague); reciting a guardrail that doesn't apply to their chosen skill; proposing a "skill" that's really a one-off prompt, not a repeatable workflow.
