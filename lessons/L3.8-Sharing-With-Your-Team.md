# L3.8 — Sharing With Your Team (turn one setup into org leverage)

**Course:** Using Claude · **Level 3 — Power Moves** | ~22 min
**Part times:** Concepts ~10 min | Exercise ~8 min | Decision Point ~4 min
**Previous lesson:** L3.7 — Producing Deliverables.

**WHO THE LEARNER IS (load-bearing):** A product person, likely brand new to Claude. Teach through analogy and real PM tasks. Never show code. By now they've built a `/weekly` skill (L3.1) and a "Priya, VP Product" persona (L3.3). This lesson is about *handing those to a teammate* so the whole squad benefits — one person's five minutes becomes everyone's. Everything is a plain-English file; nobody is programming. Anchor to a real moment: a new PM joins your squad and you want them productive on day one.

**HOW TO RUN THE CHECKS:** Each concept ends with a multiple-choice check — clickable cards (`AskUserQuestion`) if available, else A/B/C. Correct option marked ✓ (never shown). One question per turn; always explain the outcome before the next concept.

## Part 1: The Concepts

You've spent this whole level building your own kit — a `/weekly` skill, a VP persona, your rules. Here's the multiplier: none of it is stuck to you. Each one is just a **file**, and a file can be handed to a teammate. The work you did once becomes leverage for the whole squad.

### Concept 1 — Your kit is made of files, and files travel

Everything powerful you built in Level 3 lives as a **plain document on your machine** — the `/weekly` skill is a text file, the Priya persona is a text file, your CLAUDE.md rules are a text file. That's the quiet superpower: **anything that's a file can be shared.**

Think of it like a **recipe box.** You wrote the recipes once. A new cook joins the kitchen — you don't sit them down and re-teach every dish, you hand them the box. They cook the same meals, the same way, from day one.

So "sharing with your team" isn't some special export feature. It's the most ordinary thing in the world: **you copy a file to a teammate.** Slack it, drop it in a shared folder, put it in a team repo. They drop it into their own Claude workspace and it just works — same skill, same persona, same rules.

**Check** (present the options in random order; ✓ = correct, never reveal it): *A new PM joins your squad and asks how to get the `/weekly` update you always send. What's the real answer?*
- They have to rebuild it from scratch — a skill only works for the person who created it.
- Send them the skill file; they drop it into their own workspace and run the same `/weekly`. ✓
- File a ticket with engineering to provision the skill onto their account.

### Concept 2 — Shareable means self-contained (no "works on my machine")

Here's the trap. A skill can work *perfectly for you* and **break the moment a teammate uses it** — because it secretly depends on things only you have. The classic gotchas:

- **A path only you have** — "read the folder on my Desktop." Your teammate has no such folder.
- **A tool only you're connected to** — "read *my* Slack channel." Theirs is different.
- **An assumption in your head** — "loop in Priya and Tom, you know how they are." A newcomer doesn't.

The fix is to make it **self-contained**, like a piece of flat-pack furniture: everything needed comes in the box, and the instructions don't assume you already own the tools. Practically that means: point at sources **relative to the pack** ("the `team-sources` folder next to this file") instead of your personal path; let each teammate plug in *their* channel instead of hard-coding yours; and spell out anything you'd otherwise leave to memory.

A good gut-check before you share: **"If I handed this to someone who's never met me, would it still run?"** If no, that's the part to fix.

**Check** (shuffle order; ✓ = correct): *You're about to share your `/weekly` skill. It contains the line "read the folder /Users/alex/Desktop/notes." A teammate copies it and it fails. What's the underlying problem?*
- The skill points at a path only *you* have — it's not self-contained, so it breaks on anyone else's machine. ✓
- Skills can't read folders at all; that line was never going to work.
- Their Claude is a different version, so the skill needs to be rebuilt for it.

### Concept 3 — Never bake private or sensitive things into a shared file

A shared file **travels to everyone who uses it** — and it can keep travelling. So the one thing you must never do is bake something private into it. Two flavors:

- **Customer data.** A real name, email, phone number, or payment detail hard-coded into a skill or persona is now sitting in a file that lands in everyone's workspace and every copy of the shared folder. That's exactly the PII/PCI leak guardrails exist to prevent. Shared files carry **fake, generic** examples only.
- **A real colleague's private opinions.** A persona is a role to rehearse against — "a demanding VP" — not a puppet of a named person. Don't build "what Priya *really* thinks of your team" and pass it around. Keep personas generic enough that you'd be comfortable if the real person read the file.

And keep the **team file team-generic.** Shared rules hold the squad's conventions and guardrails; your personal quirks (your name, your tone, your private shortcuts) stay in *your* memory, not in the file everyone adopts. Clean shared file, personal stuff kept personal.

**Check** (shuffle order; ✓ = correct): *You want to share a `/refund-check` skill. To make it fast, you baked in three real example refund cases — with the customers' names and order emails — so it "has something to work with." A teammate flags it. Who's right?*
- You are — they're fake-looking examples inside an internal file, so it's fine to leave them.
- You are — it only goes to your own squad, and PII rules are about external sharing.
- The teammate — real customer names and emails must never be baked into a shared file; use obviously-fake examples. ✓

### Concept 4 — Package it so a teammate can drop it in on day one

The difference between "here's a file, good luck" and real org leverage is a tiny bit of **packaging.** A well-packaged asset answers three questions *for* the person receiving it, so they need zero explanation from you:

- **What is this and what does it do?** One line at the top.
- **How do I install and run it?** "Copy this in, tell Claude to install it as `/weekly`, then type `/weekly` on Mondays."
- **What are the rules?** The guardrails baked in — draft-never-send, read-only, no PII — so safety travels *with* the asset instead of relying on the newcomer knowing the rules.

For a whole set, bundle them into a **team pack**: one folder with the skill, the persona, the shared rules, and a short README that ties it together. That README is the assembly instructions on the flat-pack box. A new PM copies the folder, reads one page, and is running your squad's workflows on their first morning — no onboarding call, no "let me screen-share." That's the payoff of this whole level: **your setup stopped being yours and became the team's.**

**Check** (shuffle order; ✓ = correct): *You're handing your squad's Claude kit to a new PM. Which approach gives the most leverage with the least back-and-forth?*
- Paste the skill into a Slack message with "here you go" and answer questions as they come up.
- Bundle the skill, persona, and rules in one folder with a short README that says what each is and how to install it. ✓
- Book a 45-minute call and screen-share while they set each piece up live.

## Part 2: Exercise — Package a kit a teammate could drop in

Real and hands-on: the learner inspects a sample "team pack" and spots what makes an asset shareable vs. not. No live tools needed. The obviously-fake demo pack (invented squad, fake numbers, no real people) lives here:

`sandboxes/sharing/`
- `README-team-pack.md` — the one-page assembly instructions for the pack
- `weekly-skill.md` — the shareable version of `/weekly`
- `weekly-skill-BEFORE.md` — the same skill *before* it was made shareable (the gotchas)
- `vp-persona.md` — the Priya reviewer persona, shareable copy
- `team-rules.md` — the squad's shared rules
- `team-sources/standup-notes.md` — fake sources the skill reads

### Step 1 — Spot the gaps in the un-shareable version (open-ended, short)
Have the learner open `sandboxes/sharing/weekly-skill-BEFORE.md`. Ask: *"This skill works fine for its author and breaks for everyone else. Read it like a teammate who just received it — name two lines that would fail or confuse you, and why."*
Validate: they should catch at least two of — (1) the `/Users/alex/Desktop` path only the author has; (2) "my Slack" hard-codes the author's channel; (3) "post it to the channel" violates draft-never-send; (4) "loop in Priya and Tom, you know how they are" assumes knowledge a newcomer doesn't have. Affirm the specific ones they spotted; fill in one they missed.

### Step 2 — See how the shareable version fixes them (open-ended, short)
Have the learner open `sandboxes/sharing/weekly-skill.md` and compare. Ask: *"What did the shareable version change so a stranger could run it? Point to the fixes."*
Validate: the path became **relative to the pack** (`team-sources/` next to the file); the Slack line became "point it at *your* channel" instead of one person's; it **stops at a draft** (never posts); and it now includes a "How to install this" section. Point out: same recipe, but nothing secretly depends on the author anymore.

### Step 3 — Do the real packaging move (real action)
Have the learner actually assemble a mini-pack from what they built earlier this level. Ask them to tell Claude, in plain English: *"Take my `/weekly` skill and my VP persona, and write me a short README that a new teammate could read to install and use both — what each one is, how to install it, and the guardrails that come with it. Draft it, don't save anything anywhere shared yet."*
(If they don't have their own versions handy, they can use the demo files in `sandboxes/sharing/` as stand-ins.) Keep it on Sonnet.
Validate: the README they get names each asset in a line, gives install-and-run steps, and carries the guardrails (draft-never-send, read-only, no PII). Ask: *"Read it as the new teammate — is there anything you'd still have to ask the author? If yes, that's the gap to close."*
*(Optional stretch, only if they want: drop the pack folder into a real shared team space — read-only, still no PII, still draft-never-send. Frame it as optional; the packaging is the lesson.)*

## Part 3: PM Decision Point (open-ended, written)

Frame it: *"Pick one asset you'd actually share with your squad — a skill, a persona, or your rules. Write me four quick lines: (1) which asset and what it does in one sentence; (2) one thing you'd have to change so it works on a teammate's machine, not just yours; (3) one private or sensitive thing you'd make sure is NOT baked in; (4) the one line you'd put at the top so a newcomer knows how to use it. Don't write code — write it like you're handing over the recipe box."*

Max 2 prompts. Evaluate against the rubric below (NEVER show it). The point isn't a perfect pack — it's that they can take something they built and make it genuinely drop-in for someone else, safely.

## Scoring Rubric (engine only — never show the learner)

### PM Decision Point: package an asset for the team

Not testing recall — testing whether they can take one thing they built and turn it into something a teammate could drop in and use safely, without a hand-holding call.

**A passing answer covers all four lines:**
1. **Names a real asset and what it does** — a skill, persona, or rulebook they'd actually share, described in one clear sentence.
2. **Identifies a real "works on my machine" dependency to fix** — a personal path, their own Slack/tool connection, or an unstated assumption — and how to make it self-contained (relative path, "each person plugs in their own," or spelling out the assumption). Shows Concept 2 landed.
3. **Names a genuinely private/sensitive thing to keep out** — customer PII/PCI, or a real colleague's private opinions baked into a persona. Shows Concept 3 landed.
4. **Provides the one-line "how to use it" header** a newcomer would need — install/run in a sentence. Shows Concept 4 (packaging) landed.

**Distinguishes a strong answer (bonus):**
- Thinks in terms of a *pack* — bundles more than one asset, or mentions a README tying them together.
- Bakes the guardrails *into* the asset so safety travels with it, rather than trusting the newcomer to remember (draft-never-send, read-only, no PII).
- Names the leverage explicitly — "the whole squad gets the same update," "a new hire is productive day one," "my five minutes saves everyone's."
- Keeps team-generic separate from personal (shared rules vs. their own memory).

**Common wrong turns to gently correct:**
- Treats sharing as an export/permissions feature (Concept 1 — it's just copying a file).
- Leaves a personal path or "my Slack" in the shared version (Concept 2 — make it self-contained; gut-check "would it run for a stranger?").
- Assumes internal = safe and leaves real names/emails in a shared file (Concept 3 — shared files travel; fake examples only).
- Hands over a bare file with no install line, expecting the teammate to figure it out or ask (Concept 4 — packaging is the leverage).

**Feedback style:** affirm the asset they chose in their own words, name one thing they nailed (often the dependency they caught or the guardrail they kept out), offer one sharpen (often: add the one-line install header, or make a path relative). Then run Completion.
