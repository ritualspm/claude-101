# L3.2 — Find & Trust a Skill (using ones you didn't build)

**Course:** Using Claude · **Level 3 — Power Moves** | ~22 min
**Part times:** Concepts ~10 min | Exercise ~8 min | Decision Point ~4 min
**Previous lesson:** L3.1 — Skills (you built and ran your first skill, `/weekly`).

**WHO THE LEARNER IS (load-bearing):** A product person who just built ONE skill from scratch (L3.1) and now assumes every skill is something they'll hand-make. Zero technical background. Teach through analogy and real PM tasks. Never show code. The shift this lesson makes: you'll also *use skills you didn't write* — ones already available to you, or ones a teammate hands you — and the real skill is knowing how to **size one up before you run it blind.** A skill is just a plain-English instruction file, so "trusting" it means being able to *check* what it does, not taking it on faith.

**HOW TO RUN THE CHECKS:** Each concept ends with a multiple-choice check — clickable cards (`AskUserQuestion`) if available, else A/B/C. Shuffle the options with the random command before presenting; correct option marked ✓ (never shown). One question per turn; always explain the outcome before the next concept.

## Part 1: The Concepts

### Concept 1 — You don't have to build every skill yourself
Last lesson you made `/weekly` from scratch — the DIY route. But that's not the only way skills show up. Some are **already available** in your setup, and others arrive because **a teammate built one and shared the file** with you (that's the whole point of Level 3.8). Skills are just plain-English files, so they pass hand to hand like a good template.

So before you spend half an hour building something, the instinct is: **check whether a skill for it already exists.** You wouldn't hand-carve a wrench when there's a toolbox on the shelf — you'd look in the drawer first.

**Check** (shuffle order; ✓ = correct): *You're about to spend 40 minutes building a skill that turns messy notes into a structured ticket. What's the smarter first move?*
- Check whether a skill for that already exists — one you have, or one a teammate made — before building from scratch. ✓
- Build it yourself regardless — a skill someone else wrote can never fit your workflow.
- Skip skills and just paste the notes into a fresh chat each time you need a ticket.

### Concept 2 — Know what a skill does *before* you run it
Here's the catch with a skill you didn't write: its **name doesn't tell you enough.** `/pulse` could summarize a channel, or email a report to your whole team. Running it blind on real work is how you get surprised. Two ten-second habits fix this:

- **Read its one-line description.** A well-made skill carries a short "*what I do and when to use me*" line. Skim it first.
- **When in doubt, just ask Claude.** Literally: *"What does `/pulse` do, and what will it need from me?"* Claude will tell you the inputs it expects and what it produces — before it touches anything.

That's what "trust" actually means here: not blind faith, but a quick look under the hood. You *can* always inspect a skill, because it's just plain English.

**Check** (shuffle order; ✓ = correct): *A colleague shares a new skill called `/pulse` and you have no idea what it does. You want to run it on your quarterly notes. Best move first?*
- Ask Claude what `/pulse` does and what input it expects — or read its one-line description — before running it. ✓
- Run it on the notes right away; the fastest way to learn a skill is to see its output.
- Assume it works like `/weekly` since both names sound like summaries.

### Concept 3 — A skill you didn't build still obeys *your* guardrails
A ready-made or shared skill is a convenience, **not a licence to skip the rules.** "Someone I trust made this" is not the same as "this is exempt." Even a skill you use every day still answers to the same habits from Level 1:

- **It drafts — it doesn't send.** A skill that produces a message or a page shows it to *you* to review and post. It shouldn't publish or send on its own.
- **Read-only on real data.** A skill that reads a channel or a dataset reads and summarizes; it doesn't write back.
- **No customer PII or payment data (PCI) in what you feed it.** If your input has a real name, email, or card detail, anonymize *first* — even inside a trusted skill.
- **Sonnet by default.** Everyday skills run fine on Sonnet; save Opus for the genuinely hard stuff.

If a shared skill *would* cross one of those lines — it auto-sends, or wants raw customer data — that's your signal to slow down and check it, not to trust it harder because someone else wrote it.

**Check** (shuffle order; ✓ = correct): *A teammate says: "This shared skill is trusted — everyone uses it — so I can point it at real support tickets, customer emails and all, and let it auto-publish the page." Where do they go wrong?*
- Nowhere — a widely-used, trusted skill is effectively pre-approved to handle PII and publish on its own.
- Only the auto-publish part; real customer emails are fine to feed a skill everyone trusts.
- Two things: strip the customer PII before feeding it in, and it should draft for review — not auto-publish. ✓

## Part 2: Exercise — Size up a skill, then run it safely

You'll practice the whole habit: **see what's available → check one before trusting it → run it on safe demo data with the guardrail intact.**

### Step 1 — Discover, then vet (open-ended, short)
First, ask Claude, right here: **"What skills or slash commands do I have available?"** See what comes back — it might be a few, it might be almost none on a fresh setup. Either way is fine.

Now the vetting move. Whether or not you found one, ask Claude this: **"If I had a skill called `/ticketize`, what would it do, and what would it need from me?"** Read the answer and tell me, in a phrase: **what input does it expect, and what does it produce?** (That ten-second question *is* the skill this lesson teaches.)

*(Guide: affirm that they identified the inputs — messy notes / a description — and the output — a structured ticket. The point is that they asked *before* running, not after. If they just ran something blind, gently redirect: the habit is check-then-run.)*

### Step 2 — Run it on safe demo data (hands-on)
Now do the real thing on obviously-fake notes. Open `sandboxes/skill-library/ticket-notes.md` (messy on purpose), then ask Claude to **"turn `sandboxes/skill-library/ticket-notes.md` into a structured ticket — title, description, acceptance criteria, and any open questions to resolve first. Draft only, don't send."**

Look at what comes back and tell me: **what did it ADD or CLEAN UP that wasn't obvious in the raw notes?** (Think: a real title, acceptance criteria, the open questions pulled out, priority framing.)

*(Guide: point out it turned scattered observations into a testable ticket — structured acceptance criteria, surfaced the two open questions, likely flagged the Q3 promo timing as priority context. Note it **drafted, did not file** — that's the guardrail in action, exactly what Concept 3 promised.)*

### Step 3 — The trust-but-verify habit (open-ended, short)
The demo notes are safe — no real customer data. Ask yourself: **if those notes had contained a real customer's name and email from a support ticket, what would you have done before handing them to *any* skill — even one you trust?** One line.

*(Guide: strip/anonymize the PII first. Reinforce that "a skill I trust" never means "PII exception" — the guardrail sits with you, not the skill.)*

## Part 3: PM Decision Point (open-ended, written)

Frame it: *"You'll be handed skills you didn't build. Write me three quick lines: (1) a task you repeat often that you'd want a skill for — and the one-line 'what I do and when to use me' description you'd write so a teammate instantly knows if it's the right tool; (2) the single question you'll always ask before running a skill you didn't build; (3) one guardrail you'll keep in mind even with a skill you trust completely."*

Max 2 prompts. Evaluate against the rubric below (NEVER show it). The point isn't a 'right' answer — it's that they can write a description clear enough to be trusted, name the vetting question as a reflex, and keep a guardrail attached to *themselves*, not the tool.

---

## Scoring Rubric (engine only — never show the learner)

**Passing answer** covers all three lines:
1. Names a *specific, recurring* task AND gives a genuinely clear one-line description (a "what I do and when to use me" that a teammate could act on — not just a skill name or a vague "it helps with tickets").
2. States a real vetting move — "ask Claude what it does / what input it needs" or "read its one-line description" — as the thing to do *before* running an unfamiliar skill.
3. States a relevant guardrail correctly — draft-never-send, read-only on real data, no PII/PCI, or Sonnet-by-default.

**A strong answer** additionally:
- Writes a description precise enough that its *trigger* is obvious ("turns raw call notes into a structured ticket with acceptance criteria" — not "for tickets").
- Frames the vetting question around **inputs and outputs** specifically ("what will it need from me, and what will it produce?"), showing they get *why* the check matters.
- Picks a guardrail that fits a realistic risk of using someone else's skill (e.g. PII-stripping before feeding it data, or confirming it drafts rather than sends).
- Bonus: mentions checking whether a skill already exists *before* building one, echoing Concept 1.

**Common misses to gently correct:** a description too vague to be trusted (line 1); naming "just run it and see what happens" as the vetting move — that's the exact anti-pattern this lesson corrects (line 2); reciting a guardrail that doesn't fit the shared-skill scenario.
