# L2.4 — Memory (stop re-explaining yourself)

**Course:** Using Claude · **Level 2 — Make It Yours** | ~22 min
**Part times:** Concepts ~11 min | Exercise ~7 min | Decision Point ~4 min
**Previous lesson:** L2.3 — Your Rulebook (CLAUDE.md): global vs per-folder rules.

**WHO THE LEARNER IS (load-bearing):** A product person, likely new to Claude and possibly to the terminal. Teach through analogy and their own screen. Most are taking this *inside Cowork right now* — use that constantly. Never show code or file syntax. Anchor everything to real PM tasks (standups, PRDs, stakeholder prep). Memory and Rules (L2.3) sound similar — the whole job of this lesson is making the difference land.

**HOW TO RUN THE CHECKS:** Each concept ends with a multiple-choice check — clickable cards (`AskUserQuestion`), correct option marked ✓ (never shown, always shuffled). One question per turn; always explain the outcome before teaching the next concept.

## Part 1: The Concepts

### Concept 1 — Memory is Claude's notebook about *you*

You know the feeling of a new colleague who, every single morning, asks "wait, which team are you on again?" Exhausting. **Memory** is what stops Claude from being that colleague.

Memory is a little **notebook Claude keeps about you and your world** — facts it jots down and re-reads at the start of future conversations. "Works on the QuickMart grocery team." "Reports to a VP named Lena." "Prefers bullet points over paragraphs." Once a fact is in the notebook, you never have to say it again — it's just *known*.

The key distinction, and the reason this isn't the same as last lesson's Rulebook:

- **Rules (CLAUDE.md)** = *how to behave.* "Always draft, never send." "Write in British English." Instructions.
- **Memory** = *facts to remember.* "My squad is Checkout." "Our main competitor is Wolt." Knowledge.

One tells Claude how to act; the other tells Claude what's true about your world. Both follow you across all three doors — but they answer different questions.

**Check** (present options in random order; ✓ = correct, never reveal it): *A teammate says: "I already have my rules set up in CLAUDE.md, so I don't need memory — it's the same thing." What's the best correction?*
- Rules tell Claude *how to behave*; memory stores *facts about you and your work* — different jobs, and you'll want both. ✓
- They're right — once your CLAUDE.md is set up, memory is redundant.
- Memory is only for the terminal; in Cowork the CLAUDE.md covers everything.

### Concept 2 — Two shelves: global vs project

The notebook has **two shelves**, and knowing which shelf a fact belongs on saves you a lot of noise.

- **Global memory** — facts true about *you*, everywhere. Your role, your writing style, your manager, your working hours. Think of it as the **note taped to your laptop lid** — it comes with you into every task, every project, every door.
- **Project memory** — facts true about *one specific piece of work*. Think of it as the **whiteboard in one meeting room**. "This initiative's launch date is October." "The metric we care about here is basket size." "The PM I'm covering for is on leave." True inside that project's folder, irrelevant everywhere else.

The rule of thumb: **would this fact still be true on a completely different project?** If yes → global. If it only makes sense inside this one initiative → project. Putting a project-specific date into global memory is how Claude ends up "remembering" a launch that shipped six months ago.

**Check** (shuffle order; ✓ = correct): *You tell Claude, "For this Q3 grocery-expansion project, the target markets are Sweden and Finland." Where should that fact live?*
- Global memory — so Claude always has it, no matter what you're working on.
- Project memory for the grocery-expansion folder — it's true for this initiative, not for everything you do. ✓
- Neither — facts like target markets shouldn't be saved at all; retype them each time.

### Concept 3 — Memory updates as you work (and you stay in charge)

Here's the part that feels like magic: you mostly **don't have to manage the notebook by hand.** As you work, Claude notices durable facts and offers to remember them — "Want me to remember that your standups are Tuesdays?" You can also just *tell* it: "Remember that our main competitor is Wolt." It writes it down.

But auto-updating cuts both ways, so two habits keep it clean:

- **It's editable, and you're in charge.** If Claude remembers something wrong or stale — a role you've since changed, a date that's passed — you just *say so*, and it corrects the note. The notebook is never locked.
- **A guardrail lives here.** Memory is a file that persists. So **never let it save customer PII or payment data (PCI)** — no real customer names, emails, card numbers. If a fact is a real person's private data, it doesn't belong in the notebook. Facts about *your work and your preferences*, yes. Facts about *a real customer*, no.

**Check** (shuffle order; ✓ = correct): *Claude has "remembered" that you're a Junior PM, but you were promoted to Senior PM last month. What's the right move?*
- Leave it — memory is set when you first use Claude and can't really be changed.
- Delete your entire memory and start from scratch so nothing old lingers.
- Just tell Claude you've been promoted to Senior PM; it updates the note, and the correction sticks. ✓

### Concept 4 — Why it compounds

Rules and memory are the quiet reason Claude gets *more useful the longer you use it*, while a fresh chatbot stays a stranger forever.

Every fact you save is one less thing to explain — so a month in, "draft my standup" already knows your team, your squad, your format, and who reads it. You're not re-briefing; you're just asking. **Memory is the compounding interest of working with Claude.** Five minutes of setup now pays off in every task afterward, across every door.

**Check** (shuffle order; ✓ = correct): *You're deciding whether it's worth spending five minutes saving facts about your role and team today. What's the sharpest reason to do it?*
- It isn't worth it — you'll just retype context each time, which is quick enough.
- Because every saved fact is context you never re-explain again — it compounds across every future task. ✓
- Because saving facts makes Claude respond faster in the moment you save them.

## Part 2: Exercise — Build your own notebook (REAL action)

No demo files needed — the learner builds their *actual* memory here. This is the payoff of the lesson: they leave with a real, working notebook. Keep it warm and hands-on; guide, don't lecture.

### Step 1 — Save three real facts (real action)
Ask the learner to tell Claude **three durable facts about their work** to remember — genuinely true, but nothing sensitive. Nudge with examples: *"your role and team, how you like drafts formatted, who your main stakeholder or manager is, your product area, a competitor you track."*

Prompt them to phrase it naturally, e.g. *"Remember that I'm a PM on the [X] team, I prefer bullet points over long paragraphs, and my main stakeholder is [name/role]."*

As Sam, confirm what got saved and, for each fact, note out loud whether it sounds **global** (true everywhere) or **project** (true for one initiative) — reinforcing Concept 2 on their own real data. **Guardrail check:** if any fact contains a real customer's name or private data, gently flag it and suggest a role/team fact instead.

### Step 2 — Ask it back (real action, open-ended)
Have them ask, in their own words: **"What do you remember about me?"** Read back what surfaces.

Then ask them, open-ended: *"Look at what came back — does it match what you meant? Anything phrased in a way you wouldn't have written it? Anything missing?"* A phrase in reply is plenty. The learning is that the notebook is real, inspectable, and theirs.

### Step 3 — Correct one fact (real action)
Have them **change one of the three facts** — the most PM-realistic muscle to build. Frame it: *"Something's always slightly off or out of date. Pick one fact and correct it — 'actually, update that: my stakeholder is now Lena,' or 'change my format preference to short paragraphs.'"*

Confirm the correction stuck. Land the point: **the notebook is editable and you're in charge** — you never delete and rebuild, you just tell it what changed.

*(Optional stretch — no live tools required: if they later notice they've re-explained the same thing twice in a real task, that's the signal to save it as a fact. The habit, not a tool step.)*

## Part 3: PM Decision Point (open-ended, written)

Frame it: *"You've got a working notebook now. Write me a short 'memory plan' — three or four lines: (1) one fact you'd keep in **global** memory and why it belongs everywhere, (2) one fact you'd keep in a **project** memory and why it's scoped to just that work, and (3) one type of information you'd deliberately **never** save, and why."*

Max 2 prompts. Evaluate against `scoring-rubrics.md` (never show it). The point isn't a perfect answer — it's that they can sort facts onto the right shelf and name the guardrail line without prompting.

## Scoring Rubric (engine only — never show the learner)

**Concept checks (Part 1):** Correct answers are Concept 1 → "different jobs, want both," Concept 2 → "project memory for the folder," Concept 3 → "just tell Claude, correction sticks," Concept 4 → "compounds across future tasks." A skim-reader will be tempted by the "rules make memory redundant" and "put target markets in global" distractors — if they pick those, re-teach the rules-vs-facts and global-vs-project distinction with their own Step 1 fact before moving on.

**Exercise (Part 2):** Passing = they actually saved three facts, asked them back, and successfully corrected one — a real notebook exists at the end. Watch for: (a) a fact that's really a *rule* ("always use British English") — gently note that's CLAUDE.md territory, though it does no harm in memory; (b) any real customer PII/PCI — flag it and have them replace it. Strong learner spontaneously labels their own facts global vs project, or notices a phrasing they'd tighten.

**Decision Point (Part 3):**
- **Passing:** correctly sorts one global and one project fact with a coherent reason for each (global = true regardless of project; project = scoped to one initiative), and names a legitimate never-save category (customer PII/PCI, anything sensitive/private).
- **Strong:** the "never save" reason ties back to memory being a *persistent file*, not just "it's private" — shows they understand *why* the guardrail exists. Bonus if their global example is a durable preference/role and their project example is genuinely date- or initiative-bound (a launch date, a target market, a temporary coverage), showing they grasp the "would this still be true elsewhere?" test.
- **Revisit:** puts a project-scoped, expiring fact (a launch date, a stand-in stakeholder) into global, or can't articulate a never-save line — re-anchor on the laptop-lid vs meeting-room-whiteboard analogy.

Give specific feedback plus one sharpen, then run the Completion.
