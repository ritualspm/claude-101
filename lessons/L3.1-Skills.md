# L3.1 — Skills (turn a repeated workflow into one command)

**Course:** Using Claude · **Level 3 — Power Moves** | ~23 min
**Part times:** Concepts ~11 min | Exercise ~8 min | Decision Point ~4 min
**Previous lesson:** L2.8 — Responsible & Safe Use.

**WHO THE LEARNER IS (load-bearing):** A product person, likely brand new to Claude. Teach through analogy and real PM tasks. Never show code. A skill is *just a plain-English instruction file* — keep it that concrete; nobody is programming. This is the first hands-on Level 3 lesson: the learner will actually build and run a real `/weekly` skill on obviously-fake demo files. Anchor everything to a ritual a PM actually repeats.

## Part 1: The Concepts

You do the same rituals every week — the Monday update, the standup write-up, the release note. In L2.2 you learned Claude is one main brain that can hire helpers. This lesson is the first payoff: you'll teach that brain a **recipe** so a whole ritual runs from one word.

### Concept 1 — A skill is a saved recipe

Think of a skill as a **recipe card you write once and hand to a very fast cook.** Every time you'd normally re-explain the same multi-step task — "read these sources, pull what changed, write it in my format, keep it under 200 words" — you instead write those steps down *once*. That written-down set of steps is a **skill.**

The magic isn't that Claude does something new. It's that you stop *re-typing the same long instructions.* A task that used to be a paragraph of briefing becomes one short command. Same result, a fraction of the effort, and it comes out **the same way every time** — because the recipe doesn't drift the way your memory does on a busy Monday.

And here's the part that surprises people: a skill is **not code.** It's a plain-English document — the same kind of instructions you'd write for a new teammate. If you can write a good handover note, you can write a skill.

**Check** (present the options in random order; ✓ = correct, never reveal it): *A teammate says: "Skills are for engineers — you have to write code to make one, so I'll skip them." What's the best correction?*
- Half right — you don't code it, but only engineering can install one for you, so you still need a ticket.
- A skill is just a plain-English instruction file — like a handover note — so any PM can write one, no code involved. ✓
- True — skills are code, so unless you can program, stick to typing your instructions out each time.

### Concept 2 — You run it with a slash command

Once the recipe exists, you trigger it by typing a **slash command** — a short name with a `/` in front, like **`/weekly`**. Typing `/weekly` is you saying *"run that recipe now."* Claude reads the instructions you saved and follows them.

Two things worth knowing:
- **The name is yours to pick** — `/weekly`, `/standup`, `/release-note`. Choose something you'll remember. Short and obvious beats clever.
- **You can hand it context on the fly.** `/weekly` runs the recipe as-written; `/weekly focus on the checkout squad only` runs the same recipe but with an extra nudge. The recipe is the backbone; a few words after it steer this one run.

So the finished picture: write the recipe once → type its name whenever you need it → optionally add a nudge. That's the whole loop.

**Check** (shuffle order; ✓ = correct): *You built a `/weekly` skill. This Monday you want the usual update, but *only* covering the checkout squad. What's the efficient move?*
- Type `/weekly focus on the checkout squad only` — run the saved recipe with a one-off nudge. ✓
- Open the skill file and rewrite it to be checkout-only, then run `/weekly`.
- You can't — a skill always runs exactly as written, so type the full briefing out manually this week.

### Concept 3 — Good skills read sources and end in a draft

The weak version of a skill is just a formatting template. The **powerful** version tells Claude *where to look* and *where to stop.* Two ingredients make the difference:

- **Point it at sources.** "Read the docs in this folder / read my #squad-checkout channel." Now the skill doesn't just format — it *gathers* the week's changes for you, then writes them up. (Under the hood, that's the main Claude hiring the reading-helpers from L2.2. You just say "read these.")
- **Bake in where it stops.** A good `/weekly` ends at a **draft you approve** — it never posts to Slack on its own. You write that rule *into the recipe once*, and it holds every single run.

This is where guardrails become automatic instead of something you have to remember: put **"draft only — never send," "read-only on the sources,"** and **"no customer names, emails, or payment data"** right into the skill. Because the recipe runs the same way every time, those guardrails run every time too. You made safety the default.

**Check** (shuffle order; ✓ = correct): *You're writing a `/weekly` skill that reads your team's Slack channel and writes the update. To keep it safe by default, what belongs *inside the recipe itself*?*
- Nothing — guardrails are a Claude setting, so they apply automatically and don't belong in a skill.
- A reminder to double-check the output yourself, but posting can be automatic since it's your own channel.
- The rules: read-only on the sources, draft only / never post, and no customer PII or payment data. ✓

### Concept 4 — Build a skill once, reuse it forever (and share it)

The reason skills are a *power move* and not just a shortcut: they **compound.** The five minutes you spend writing `/weekly` today pays back every Monday for the rest of the year. And a good skill isn't stuck to you — it's a file, so a teammate can use the exact same `/weekly` and get updates in the same shape. (Sharing skills is its own lesson later; for now, just know a skill is a reusable, hand-off-able asset — not a one-time trick.)

Rule of thumb for *what* to turn into a skill: **anything you've briefed Claude on more than twice the same way.** If you catch yourself re-typing similar instructions, that's the signal — stop, and write the recipe. And keep everyday skills running on **Sonnet** — they're routine work, not hard problems.

**Check** (shuffle order; ✓ = correct): *Which of these is the best candidate to turn into a skill right now?*
- A one-off competitive teardown you were asked to do this once and probably won't repeat.
- Your Monday team update — same sources, same format, every single week. ✓
- A genuinely hard strategy call you're making for the first time and haven't figured out how to approach.

## Part 2: Exercise — Build and run your first `/weekly`

This is real: the learner will look at an example skill, then actually build and run their own on obviously-fake demo files. No live Slack needed. The demo files (invented squad, fake numbers, no real people) live here:

`sandboxes/skills/`
- `example-weekly-skill.md` — a finished sample skill to learn from
- `team-sources/standup-notes.md` — fake standup notes for the week
- `team-sources/metric-snapshot.md` — a fake metric table

### Step 1 — Read the example skill (open-ended, short)
Have the learner open `sandboxes/skills/example-weekly-skill.md`. Ask: *"Read it like a handover note. In your own words — what are the three things this recipe tells Claude: what to do, where to look, and where to stop?"*
Validate: (1) **what** — produce a Monday update in a fixed 4-section format; (2) **where to look** — the docs in `team-sources/`; (3) **where to stop** — draft only, never post, no PII/payment data. Point out there's not a line of code in it — it's plain English.

### Step 2 — Run the recipe on the demo sources (real action)
Have the learner ask Claude, in plain English: *"Follow the instructions in `sandboxes/skills/example-weekly-skill.md`, using the files in `sandboxes/skills/team-sources/` as the sources. Produce the draft."*
(This runs the recipe manually — the same thing typing `/weekly` would do once it's installed. Keep it on Sonnet.)
Confirm they get a **draft** with the four sections, pulling from the fake notes (e.g. one-tap reorder shipped behind a flag; A/B test at 5%; the +2.1pt early read flagged as *don't quote yet*; the "widen to 25%?" decision waiting on the PM; completion rate 71.0% → 73.1%). Ask: *"What did it pull into 'Needs a decision', and did it correctly refuse to quote the shaky number as fact?"* Validate that it flagged the widen-the-test decision and treated the early read cautiously — that's the recipe's "say so rather than guess" rule working.

### Step 3 — Make it yours, then install it (real action)
Ask the learner to change **one thing** in a copy of the recipe to fit their real ritual — e.g. rename the sections, add a "Risks" block, or point it at a different (fake, for now) source. Then walk them through saving it as an actual command: *"Ask Claude: 'Save this as a skill called /weekly so I can run it with one command.'"* Claude will place the instruction file where skills live and confirm the command.
Validate: they changed at least one thing deliberately (it's *their* recipe now), and they understand that from here `/weekly` runs it. *(Optional stretch, only if they want: point the real skill at a real read-only Slack channel — still draft-never-send, still no PII.)*

## Part 3: PM Decision Point (open-ended, written)

Frame it: *"Pick one ritual you actually repeat most weeks. Write me the skeleton of a skill for it in four quick lines: (1) the command name you'd type; (2) what it does, in one sentence; (3) which sources it should read; (4) one guardrail you'd bake in so it's safe every run. Don't write code — write it like a handover note."*

Max 2 prompts. Evaluate against the rubric below (NEVER show it). The point isn't a perfect skill — it's that they can spot a real repeated ritual and shape it into a recipe that reads sources and stops safely.

---

## Scoring Rubric (engine only — never show the learner)

### PM Decision Point: sketch a real skill

Not testing recall — testing whether they can (a) recognise a genuinely repeated ritual, and (b) shape it into a recipe that names sources and ends safely.

**A passing answer covers all four lines:**
1. **A sensible command name** — short, memorable, matches the task (`/weekly`, `/standup`, `/release-note`). Cleverness doesn't matter; a name that fits does.
2. **A one-sentence "what it does"** that describes a genuinely *repeated* task from their work — not a one-off.
3. **Names at least one real source to read** — a folder, a Slack channel, a docs space. Shows they grasped that a good skill *gathers*, not just formats.
4. **Bakes in at least one real guardrail** — draft-never-send, read-only, or no PII/PCI. Shows safety-by-default landed.

**Distinguishes a strong answer (bonus):**
- The task is unmistakably repeated ("every Monday", "each release") — they picked a true ritual, not a stretch.
- More than one guardrail, or they explain *why* baking it in beats remembering it each run (it runs the same every time).
- Nods to reuse/compounding — e.g. a teammate could run the same command, or "five minutes now saves me every week."

**Common wrong turns to gently correct:**
- Picks a one-off task (Concept 4 — skills are for things you repeat the same way more than twice).
- Writes a pure formatting template with no sources (Concept 3 — a strong skill says *where to look*).
- Leaves out the stop/guardrail, assuming safety is automatic (Concept 3 — bake it into the recipe so it holds every run).
- Thinks they must write code or file an eng ticket (Concept 1 — it's a plain-English file any PM can write).

**Feedback style:** affirm their chosen ritual in their own words, name one thing they nailed, offer one sharpen (often: name a concrete source, or tighten the guardrail). Then run Completion.
